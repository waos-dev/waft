---
title: Inspecting a running app
description: Ask a running debug app for its widget, render and layer trees and for pictures of its widgets, with cargo waft ext.
---
A debug build of a Waft app serves **service extensions**, as a debug Flutter app does through its VM service: named calls that answer what the app is doing right now. `cargo waft ext` calls them, from a terminal or an agent, while the app runs:

```bash
cargo waft run                                   # in one terminal: a debug build
cargo waft ext --list                            # the Waft apps running on this machine
cargo waft ext ext.waft.debugDumpApp             # the widget tree, as Flutter's debugDumpApp prints it
```

With more than one app running, name one with `--app` (its executable's name or its process id). A release build serves none.

## The trees

| Extension | Answers |
| --- | --- |
| `ext.waft.debugDumpApp` | The element tree, each widget with its properties, what it depends on, and its state or render object |
| `ext.waft.debugDumpRenderTree` | The render tree: each object's constraints, size, parent data and properties |
| `ext.waft.debugDumpLayerTree` | The layer tree the frame is composited from |
| `ext.waft.debugDumpFocusTree` | The focus tree, and which node has focus |
| `ext.waft.listServiceExtensions` | Every extension this app serves |

A dump is printed as text. In a test, the same text comes from `debug_dump_app(app)`, `debug_dump_render_tree(app)` and `debug_dump_layer_tree(app)`.

## One widget: its details and its picture

The inspector's extensions name each element and render object by an id, as Flutter's DevTools does. Ask for the tree, find the widget, and pass its `valueId` back:

```bash
cargo waft ext ext.waft.inspector.getRootWidgetTree groupName=g isSummaryTree=true
cargo waft ext ext.waft.inspector.getDetailsSubtree arg=inspector-4294967303 objectGroup=g
cargo waft ext ext.waft.inspector.screenshot id=inspector-4294967303 width=1000 height=1000 maxPixelRatio=2 > field.png
```

- **The tree** is JSON. Each node carries its `description`, its `widgetRuntimeType`, its `valueId`, and in a debug build its `creationLocation`: the file and line of your code that made the widget. `isSummaryTree=true` keeps only the widgets your own code made, leaving out those the framework builds inside them.
- **The details** of one node add its properties, `subtreeDepth` levels down (2 by default).
- **The screenshot** is that widget alone, without what paints around it, fit within `width` by `height` pixels at no more than `maxPixelRatio`, with `margin` around it. `cargo waft ext` writes its PNG to standard output. A view's root id pictures the whole view.

## Adding your own

An app or a package registers its own extensions the way the framework does, with a whole name beginning `ext.`:

```rust
use std::rc::Rc;
use waft::{ServiceExtensions, Task};

ServiceExtensions::register(app, "ext.notes.openNoteCount", Rc::new(|app, _params| {
    let count = notes(app).len();
    Task::ready(Ok(serde_json::json!({ "count": count })))
}));
```

A test calls an extension directly with `ServiceExtensions::call(app, name, params)`, without a host.

## How it is carried

The framework keeps the extensions and does no I/O. A host carries the calls: the desktop host listens on a loopback port in a debug build and lists the app in a folder only its user can read, speaking JSON-RPC 2.0 with an extension's name as the method, after a first line carrying the listing's token. Another tool can speak it too; `waft-service-protocol` has the listing, the hello and the messages.
